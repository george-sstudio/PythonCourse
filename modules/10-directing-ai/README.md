# Module 10: Briefing the AI

**Time:** about 3 hours · **Week 4** · *Not in the book. This is the main "AI era" addition.*

The first nine modules gave you enough Python and PyQGIS to *read* code and *judge* it. Now you hand over most of the typing. The quality of what comes back depends mostly on two things you control: **the brief** (what you ask for) and **the checks** (how you'll know it's right).

## You will

- know what AI is reliably good and bad at in PyQGIS work
- give the AI exact facts about your project with a **context card**, generated by a script
- write a **brief** with goal, inputs, outputs, rules and **checks**
- run the **plan → code → verify** loop in a chat, and know when to start over
- set up standing **house rules** so you don't repeat yourself

## Key words

| Word | Meaning |
|---|---|
| **Brief** | A written request with everything needed to do the job right: goal, context, inputs, outputs, rules, checks. |
| **Context card** | A factual summary of your project (layers, CRS, fields, layouts), made by `tools/describe_project.py`. |
| **Acceptance check** | A concrete test that the result is right: "13 PDFs", "Lena → Lensk, Yakutsk, Zhigansk". Written *before* the code. |
| **Hallucination** | AI output that sounds right but is invented, e.g. a method that doesn't exist. |
| **House rules** | Standing instructions (version, style, safety) given once, e.g. as Claude Project instructions. |
| **Context window** | How much of the conversation the AI can "hold in mind". Long, messy chats make it worse. |

## 1. What AI is good and bad at (for PyQGIS)

| Reliably good | Unreliable without your help |
|---|---|
| Boilerplate: imports, loops, functions, layout items | **Your data**: layer names, field names, values, quirks (`-99`) |
| Turning a Processing History command into a batch loop | **Your version**: it mixes QGIS 2, 3 and 4 code from the internet |
| Explaining code and error messages line by line | **Units and CRS**: buffering in degrees is its classic mistake |
| Translating GUI clicks you describe into code | **Silent failures**: code that "runs fine" and does nothing |
| Suggesting which Processing tool fits a task | **API details**: inventing a method that *should* exist |
| Restructuring messy code into functions | **Knowing when to stop**: it adds features you didn't ask for |

The right column is exactly what this course trained you to check. The rest of this module is about filling those gaps **up front**.

## 2. Give it the facts: the context card

The AI can't see your project. So instead of describing it from memory ("I have a countries layer with population"), let a script describe it exactly.

Open your project, then open and run `tools/describe_project.py`. You get Markdown like:

```text
## Context: my QGIS project
- QGIS 3.40.14-Bratislava (PyQGIS). Code must also work in QGIS 4.x.
- project CRS: EPSG:8857 - WGS 84 / Equal Earth Greenwich (units: meters)

### Layers (top of the Layers panel first)
- **places** - vector, Point, 1251 features
  - source: `…/data/natural_earth.gpkg|layername=places` (provider `ogr`)
  - CRS: EPSG:4326 - WGS 84 (units: degrees)
  - fields:
    - `name` (String): 'Bombo', 'Fort Portal', 'Potenza'
    - `adm1name` (String, 87/1251 NULL): 'Bamunanika', 'Kabarole', 'Basilicata'
    - `pop_max` (Integer): 75000, 42670, 69060
...
### Print layouts
- layout **Country sheet** (210 x 297 mm); item ids: `title`, `main_map`, `legend`, ...
```

Every line answers a question the AI would otherwise **guess**: exact names, types, CRS **and units**, NULL counts, layout item ids. It's also saved to `output/context_card.md`.

## 3. The brief

The full template is in [AI_PLAYBOOK.md §2](../../AI_PLAYBOOK.md#2-the-brief-template). The parts, with why each matters:

| Part | Why |
|---|---|
| **Goal** | One sentence of *what should exist*, not *how*. Lets the AI suggest a better way. |
| **Context** | The context card. Stops it guessing names, versions and units. |
| **Inputs / Output** | Exact names, paths, formats, CRS, fields. Most wrong results are wrong *outputs*. |
| **Rules** | Your non-negotiables: never touch source data, metres not degrees, no new fields… |
| **Checks** | How you'll know it worked. **The most important part**, and the one people skip. |
| **How I want the answer** | Plan first, small functions, asserts at the end. |

### A vague request vs a brief

> ❌ "Make maps of all the countries in South America."

> ✅
> **Goal:** One A4 portrait PDF per South American country, in the style of my *Country sheet* layout.
> **Context:** *(context card)*
> **Inputs:** layer `Countries` (filter `"continent" = 'South America'`), layout `Country sheet` (item ids `title`, `main_map`, `info_text`, `inset_map`).
> **Output:** `D:\PythonCourse\output\sheets\sheet_<adm0_a3>.pdf`, 300 dpi.
> **Rules:** don't change the layout's design; main map in the country's UTM zone, scale rounded up to a nice number; never write outside `output\sheets`.
> **Checks:** 13 PDFs; Brazil's map in UTM 22S or 23S; every title equals the country name; a CSV log with code, CRS, scale and file name per page.
> **Answer:** plan first; then code in functions; asserts at the end.

The second takes three minutes longer to write and saves an hour of back-and-forth.

### Writing good checks

- **Counts you know**: 13 countries, 242 features, 9 layers.
- **A named case**: "Peru's capital is Lima", "Lena → Lensk, Yakutsk, Zhigansk".
- **Units and CRS**: "the output is in EPSG:3035", "areas in km² between 1 and 20,000,000".
- **A trap case**: a name with an apostrophe, a NULL value, a high-latitude feature, an empty filter.
- **An independent estimate**: buffer area ≈ 2 × distance × line length (Module 09).

Ask the AI to turn your checks into `assert` lines. Then *you* can verify in one click, and the AI's code has to meet *your* definition of correct.

## 4. The loop: plan → code → verify

**Step 1: plan, in words.** End your brief with *"First give me a numbered plan and your assumptions. Wait for my OK."* Read the plan the way you'd read a colleague's: wrong CRS? missing step? an assumption you can correct ("no, `pop_est` is never NULL, but it can be 0")?

**Step 2: code, in small pieces.** *"Now write step 1 and 2 only, as functions, with a check after each."* Run them. Paste back the output, or the **full** traceback.

**Step 3: verify, then continue.** Asserts pass → open the output → look at it. Then the next step.

**When to start over:** if the same problem survives **two** fix attempts, stop. Open a new chat with an improved brief that includes what you learned ("note: `places` has no `population` field; it's `pop_max`"). A fresh chat with a better brief beats a long chat with ten corrections, because the failed attempts in the history keep pulling the AI back.

## 5. House rules: say it once

Some instructions apply to *everything*: your QGIS version, QGIS 4 compatibility, "never modify source data", "metres not degrees", "assert checks at the end". Put them in the **instructions of a Claude Project** (claude.ai → Projects → your project → *Instructions*) so every chat in that project starts with them. A ready-made set is in [AI_PLAYBOOK.md §3](../../AI_PLAYBOOK.md#3-house-rules-give-these-once).

Keep house rules **short**. A long list gets skimmed by people and by AI alike. Add a rule only when you catch the same mistake twice.

## 6. Other good uses of AI (beyond writing code)

- **"Which Processing tool does X?"** Then confirm with `processing.algorithmHelp()`.
- **"Explain this traceback, then tell me what to print to confirm your theory."**
- **"Here's my GUI workflow: (steps). Turn it into a script."**
- **"What could go wrong with this script on other data?"** Ask it to generate trap cases.
- **"Review this script against my brief"**, in a fresh chat (Module 11).

## Checkpoint

1. Name three things the AI can't know about your project unless you tell it.
2. Why write checks **before** the AI writes code?
3. What should the first answer to a brief be?
4. You've asked for the same fix twice and it still fails. What now?
5. What belongs in house rules, and what doesn't?

<details><summary>Answers</summary>

1. Any three of: layer and field names, field types and values (NULLs, `-99`), each layer's CRS and units, your QGIS version, layout item ids, where outputs should go.
2. So "correct" is defined by you, not by whatever the code happens to do, and so the code can check itself.
3. A plan in numbered steps with assumptions, not code.
4. Start a new chat with an improved brief that includes what you learned.
5. Rules that apply to every task (version, compatibility, safety, style). Not task-specific details, and not long explanations.
